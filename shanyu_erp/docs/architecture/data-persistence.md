# 数据持久化需求与技术方案

> 状态：设计基线  
> 日期：2026-08-31  
> 目标：保证山屿 ERP 在至少 3 年持续迭代和运行期间，业务数据正确、可追溯、可恢复、可迁移，并能够自然承接施工项目管理和财务模块。

## 1. 范围与假设

- 单公司内部使用，当前约 20 人，不按多租户 SaaS 设计。
- 一期已有项目、空间、基础库、半包报价、预计成本/毛利、审批、版本、导出和审计。
- 二期增加施工计划、进度、照片、工程变动；三期增加收付款、实际成本和实际毛利。
- 本地开发使用 PostgreSQL 与 MinIO；生产运行边界遵循 ADR-0001。
- 生产目标是云厂商提供的一台 Windows Server IaaS 云主机；云厂商未确定，因此方案不依赖某一家厂商的专有服务。
- PostgreSQL 是结构化业务事实来源，MinIO 是文件内容来源；Excel、PDF 和图片不是数据库替代品。

## 2. 持久化目标

### 2.1 正确性与一致性

- 项目从报价、施工到财务始终使用同一稳定项目 ID。
- 金额、数量和比率使用数据库定点数；不以 JavaScript 浮点数作为最终持久化结果。
- 业务不变量同时由领域模块与数据库约束保护；不能仅依赖页面校验。
- 一个业务动作涉及多张表时必须在同一 PostgreSQL 事务中完成，失败时整体回滚。
- 客户端重试不得静默创建重复审批、重复付款、重复导入或重复工程变动。
- Mutable aggregate 使用修订号进行乐观并发控制；冲突必须返回当前版本，禁止最后写入者静默覆盖。

### 2.2 版本与不可变性

- 已发布基础库版本、数量规则、已提交/已批准报价及其明细不可原地修改或删除。
- 基础库调价生成新版本；历史报价继续引用原价格、成本和规则快照。
- 报价修改生成下一版本并保留父版本关系；施工变动独立于批准报价。
- 财务入账后通过冲正或调整记录纠错，不直接改写原收付款。
- 审计事件为追加式记录；应用运行账号无权更新或删除。

### 2.3 可追溯性

- 关键变化能回答：谁、何时、在哪个项目、对什么对象、执行什么动作、结果如何、前后值是什么、原因是什么。
- 审计展示按权限脱敏；没有成本权限的用户不能从审计前后值推导成本或毛利。
- 导入批次保留源文件哈希、来源工作表、校验报告、发布人和发布版本。
- 文件记录保留内容哈希、大小、类型、归属项目、业务用途、存储版本和上传人。

### 2.4 可用性与恢复目标

生产环境目标：

| 指标 | 目标 |
|---|---|
| PostgreSQL RPO | 不超过 15 分钟 |
| 文件 RPO | 不超过 1 小时 |
| 核心业务 RTO | 4 小时内恢复登录、项目、报价、审批与财务结构化数据 |
| 完整文件 RTO | 8 小时内恢复合同、导出、材料图片和现场照片 |
| 备份恢复演练 | 上线前 1 次；上线后每季度至少 1 次 |

RPO 是可接受的最大数据丢失时间，RTO 是从故障发生到恢复可用的时间。Docker 命名卷只能让容器重建后继续使用数据，不属于备份。

### 2.5 安全与保密

- 数据库、MinIO、备份仓库均不直接暴露公网。
- 生产流量使用 TLS；数据盘和备份使用静态加密。
- 应用不得使用 PostgreSQL 超级用户或 MinIO root 凭据。
- 数据库至少分为迁移账号、应用运行账号、只读运维账号和备份账号。
- MinIO 至少分为管理账号、应用桶账号和备份/复制账号，并按桶和前缀最小授权。
- 密码、Cookie token、访问密钥和备份加密密钥不得进入 Git、日志或导出文件。

## 3. 数据分类与保留策略

三年是运行下限，不等于三年后自动删除。当前规模下，保留结构化业务历史的成本远低于误删风险。

| 数据类别 | 示例 | 默认保留 |
|---|---|---|
| 核心业务主数据 | 项目、空间、用户、项目指派、主材 SKU | 不自动硬删除；通过停用、作废或归档表达状态 |
| 不可变业务版本 | 已发布基础库、报价版本、审批、工程变动、结算版本 | 长期保留；至少覆盖项目生命周期及公司确定的档案期限 |
| 财务记录 | 应收、收款、应付、付款、实际成本、冲正 | 不自动删除；三期上线前由财务确认最终档案期限 |
| 审计事件 | 登录、编辑、审批、调价、导出、权限变化 | 在线保留至少 3 年，推荐 7 年；归档后仍可按项目查询 |
| 关键文件 | 合同、客户确认报价、签字选材单、工程变动单、结算资料 | 与对应业务记录同寿命，不使用自动过期规则 |
| 施工照片 | 现场进度、巡检、隐蔽工程照片 | 项目结项后至少 3 年，具体期限在二期确认 |
| 可再生成文件 | 未签字的 PDF/XLSX 导出 | 批准版本产物长期保留；草稿导出可在 90 天后清理 |
| 临时数据 | 未完成上传、导入临时文件、解析缓存 | 失败或未引用记录 7 天后清理 |
| 会话数据 | 已过期或已撤销登录会话 | 过期 90 天后清理；保留对应安全审计 |

任何自动清理任务都先产出待清理清单和数量，业务数据不得使用无审核的级联删除。

## 4. 目标技术结构

### 4.1 PostgreSQL：结构化业务事实来源

继续使用 PostgreSQL 18。官方支持策略为每个主版本提供 5 年支持；PostgreSQL 18 支持至 2030 年 11 月，覆盖本项目的三年运行目标。生产环境应按季度评估并升级到当前 18.x 小版本；最迟在停止支持前 6 个月完成下一主版本演练。

数据建模原则：

- 关系表保存项目、成员、工程项、SKU、报价行、审批、计划、变动和财务流水。
- JSONB 只用于结构可变但不承担核心关联的内容，如规则快照、校验报告和审计前后值。
- 业务关联使用外键；状态、正数、唯一性和版本完整性使用数据库约束。
- 时间使用 `timestamptz` 并以 UTC 持久化，界面按 Asia/Shanghai 展示。
- 业务 ID 使用 UUID；外部展示编号是可变显示属性，不作为关联主键。
- 大型二进制文件不存入 PostgreSQL。

当前方案采用“当前状态表 + 不可变版本表 + 追加审计/财务记录”，不采用全量事件溯源。这样能保留关键历史，又不会让每个普通查询都依赖事件重放。

### 4.2 MinIO：文件内容来源

建立统一文件模块，业务模块只保存文件引用，不直接使用宿主机路径。

文件持久化流程：

1. API 创建“待上传”文件记录和唯一对象键。
2. 文件上传到私有 MinIO bucket，计算并校验 SHA-256、大小和内容类型。
3. 校验成功后在事务中将文件记录标记为可用并绑定业务对象。
4. 下载前由 API 校验角色、项目范围和敏感级别，再返回短时有效地址或代理下载。
5. 未完成上传和无引用对象由独立清理任务处理。

对象键使用不可猜测 ID，不在键名中放客户姓名、地址或手机号。启用 bucket versioning；应用使用“新对象代替旧对象”，不覆盖同一对象。关键桶不配置自动删除业务对象的生命周期规则。

建议至少分为：

- `erp-business`：合同、材料图片、施工照片、批准导出等业务文件；
- `erp-temporary`：未完成上传、解析文件和可再生成的草稿导出；
- 异机备份仓库：位于不同服务器或不同云账号，不与生产 MinIO 共用故障域。

### 4.3 持久化模块接缝

- 每个领域模块拥有自己的 repository interface 和 PostgreSQL adapter；不建立包含所有表操作的通用仓库。
- PostgreSQL 事务是模块内部实现细节，调用方以业务动作作为 interface。
- 文件模块提供保存、读取、验证、绑定和归档的窄 interface；MinIO adapter 与测试用内存 adapter 是两个真实 adapter。
- 备份恢复属于运维能力，不包装成业务模块，也不允许业务代码直接执行备份命令。
- 当前模块都在同一 PostgreSQL 实例内时使用本地事务；只有出现企业微信、外部财务等真实异步集成后才增加事务外发箱。

### 4.4 Windows Server 云主机部署边界

云主机属于 IaaS。云厂商负责物理机房、物理网络、宿主硬件和其自身虚拟化平台；山屿仍负责客户数据、账号、Windows Server、Hyper-V、Ubuntu、容器、PostgreSQL、MinIO、备份策略和恢复验证。云盘耐久性、实例自动迁移和服务 SLA 不能证明业务数据可恢复。

沿用 ADR-0001 时，数据路径为：

`云厂商物理设施 → Windows Server 云主机 → Hyper-V Ubuntu LTS → Docker volume → PostgreSQL / MinIO`

该路径技术可行，但外层云虚拟化与内层 Hyper-V 形成双层 hypervisor，会增加存储、网络和故障排查复杂度。因此部署优先级为：

1. Windows Server 必须复用时：Hyper-V Ubuntu 运行 Web/API，优先使用托管 PostgreSQL 和云对象存储。
2. 必须把完整栈放在该 Windows Server 时：PostgreSQL/MinIO 放在 Ubuntu Guest 内，并把 pgBackRest 和对象副本发送到云主机之外。
3. Windows Server 尚未采购且没有其他 Windows 负载时：直接使用 Linux 云主机比嵌套 Hyper-V 更简单。

不建议把 PostgreSQL、MinIO 和 Node.js 分别安装成 Windows 原生服务；这会让本地与生产运行方式分叉，增加三年升级和恢复成本。

部署要求：

- 采购前由云厂商书面文档或实际测试确认实例规格支持 Hyper-V/嵌套虚拟化；不支持时改用独立 Linux 云主机，不在 Windows Server 上使用 Docker Desktop 承载生产。
- Windows 系统盘不保存唯一业务数据。Ubuntu 虚拟机文件和持久化数据位于独立加密云数据盘，便于扩容、迁移和故障重建。
- PostgreSQL、MinIO、API 不开放公网端口；公网只开放 HTTPS，Windows/Ubuntu 管理入口使用安全组白名单、VPN 或堡垒机。
- Windows 和 Ubuntu 都配置补丁窗口、重启顺序与 Hyper-V 虚拟机自动启动；生产 Compose 配置 `restart` 与健康检查，但自动重启不等于高可用。
- Windows 宿主机、Ubuntu 虚拟机和 Docker volume 都只是同一运行故障域；备份必须离开该云主机。

如云厂商提供可接受价格的托管 PostgreSQL 和对象存储，长期更推荐：

`Windows/Ubuntu 仅运行反向代理、Web、API → 托管 PostgreSQL + 云对象存储`

该方案减少数据库补丁、WAL 归档、磁盘扩容和 MinIO 运维工作，应用仍通过 PostgreSQL 与 S3 兼容边界访问，不改变领域模型。选择托管服务后仍需自行配置备份保留期、PITR、跨区域/跨账号副本、访问权限、加密、生命周期和恢复演练，不能直接采用服务默认值。

## 5. 不同领域的持久化要求

### 5.1 项目

- 项目是跨三期稳定根对象，不因转施工或进入财务重新创建。
- 已被报价、施工或财务引用的项目不得硬删除；使用作废/归档状态。
- 客户资料变化保留审计；后续如需匿名化，必须与合同和财务留档要求一起设计。

### 5.2 基础库

- 标准工程项、主材 SKU 与稳定业务 ID 分离于价格版本。
- 已发布模板、价格、成本和计算规则在数据库级阻止修改。
- 导入 staging 与发布版本分离；失败批次不能成为报价来源。
- 同一源文件哈希的重复导入必须明确复用或拒绝。

### 5.3 报价

- 草稿可修改，但每次保存使用 revision 防并发覆盖。
- 提交后冻结空间、行项目、数量、销售价、成本、规则和模板引用。
- 批准版本是后续施工、工程变动和财务的基准。
- 导出文件绑定具体报价版本和内容哈希；重新生成不能覆盖旧文件。

### 5.4 施工交付

- 施工计划需要版本；调整计划保留原计划和确认记录。
- 进展更新、节点确认和现场照片采用追加记录；更正内容通过补充记录表达。
- 工程变动独立编号、独立审批，并保存对合同金额和预计成本的影响。

### 5.5 财务

- 预计成本与实际成本分表、分口径，不能互相覆盖。
- 收款、付款和冲正为追加式财务记录；余额和利润是可重算结果。
- 外部支付或财务系统写入使用幂等业务键，防止网络重试造成重复入账。
- 三期上线前必须确认财务档案期限、银行/付款凭据的敏感级别和脱敏规则。

## 6. 备份与灾难恢复

### 6.1 PostgreSQL

生产使用 pgBackRest 管理基础备份、WAL 归档、校验、保留和恢复：

- 持续归档 WAL 到异机 S3 兼容仓库，满足 15 分钟 RPO。
- 每周完整备份，每日差异备份；保留可覆盖最近 35 天的 PITR 链。
- 每月生成一次 `pg_dump -Fc` 可移植逻辑备份，保留 36 个月；主版本升级前额外生成并验证一次。
- pgBackRest 仓库启用客户端加密；加密密钥与仓库凭据分离保存。
- 每次备份记录开始/结束时间、大小、校验结果和可恢复时间范围。

PITR 依赖连续 WAL；缺失任何必需 WAL 都可能导致恢复链失效。逻辑备份用于跨主版本迁移和选择性恢复，不能替代 PITR。

### 6.2 MinIO

- 生产业务桶启用版本控制。
- 新对象按小时以内复制或备份到异机 S3 兼容仓库。
- 关键备份桶启用对象锁或等价不可变保留，防止生产账号或勒索软件同时删除主数据和备份。
- 上传和恢复时验证 SHA-256；数据库文件记录与对象存储定期执行双向孤儿检查。
- 临时桶可设置生命周期：7 天清理未完成上传，90 天清理未引用草稿产物。

### 6.3 故障域

以下内容不能算作异机备份：

- 与生产 PostgreSQL 位于同一 Docker volume 的副本；
- 与生产 MinIO 位于同一 Linux 虚拟机或同一物理云盘的副本；
- Windows Server 宿主机上的同盘目录；
- 使用同一高权限凭据、可被一次误操作同时删除的远端桶。

最低要求是生产数据、服务器外备份和受限/不可变备份三个恢复层次。RAID、云盘快照或 MinIO versioning 均不能单独替代备份。

### 6.4 恢复演练

恢复演练必须在隔离环境执行：

1. 从完整备份和 WAL 恢复到指定时间点。
2. 执行所有数据库约束和业务烟雾测试。
3. 恢复业务文件并按哈希抽查。
4. 检查数据库引用但对象缺失、对象存在但数据库无引用的差异。
5. 记录真实 RPO、RTO、步骤、失败点和改进项。

只验证“备份任务成功”不算恢复演练。

### 6.5 云快照的定位

云主机或云盘快照用于快速重建 Windows、Ubuntu 虚拟机配置和普通文件，是第三层恢复手段，不是数据库主备份：

- 运行中快照通常只承诺崩溃一致或文件系统一致，未必与 PostgreSQL 事务、多个虚拟磁盘和对象存储写入处于同一个业务时间点。
- 快照会完整保留已经发生的误删除、逻辑错误和勒索加密，无法替代按时间点回退的 WAL/PITR。
- 与生产实例同账号、同区域且可被同一管理员删除的快照，不满足独立备份要求。
- 可以每天创建云主机/数据盘快照并保留 7～14 天，用于快速恢复整机；数据库恢复仍以 pgBackRest + WAL 为准，文件恢复仍以异机对象副本为准。
- 云快照策略启用后必须至少演练一次“从快照创建新云盘/新实例”，并记录实际启动和校验时间。

建议保护层次：

| 层次 | 作用 | 不能替代 |
|---|---|---|
| 云盘与云主机基础保障 | 降低物理硬件故障和实例丢失概率 | 误删除、逻辑损坏、勒索和应用一致性恢复 |
| 7～14 天云快照 | 快速重建 Windows/Ubuntu 和整盘 | PostgreSQL PITR、长期保留和独立副本 |
| pgBackRest + WAL | PostgreSQL 事务一致备份和 35 天 PITR | 合同、照片和导出文件 |
| 异机/跨账号对象备份 | 保护文件及 PostgreSQL 备份仓库 | 可用性监控和实际恢复演练 |
| 月度逻辑备份 | 跨版本迁移和选择性恢复 | 连续时间点恢复 |

## 7. 数据库账号和权限

生产 PostgreSQL 不使用一个账号承担全部职责：

| 账号 | 权限 |
|---|---|
| cluster admin | 初始化和应急操作；应用不可取得 |
| migrator | 执行版本化 DDL/DML 迁移；发布窗口临时使用 |
| app runtime | 只拥有运行所需表权限；不能修改 schema、不可变版本和审计历史 |
| readonly operator | 故障诊断和经授权报表；默认不读取密码哈希和敏感成本 |
| backup | pgBackRest 所需最小备份/归档权限 |

MinIO root 只用于初始化。API 使用限定到业务桶的访问密钥，备份复制使用独立密钥。

## 8. Schema 迁移与三年升级

- 已在任何共享环境执行过的迁移文件不得修改；修正问题新增迁移。
- 生产只向前迁移，不通过 destructive `down` 回滚真实数据；应用回滚使用兼容 schema，数据修复使用新迁移。
- 发布前在生产备份恢复出的隔离副本执行迁移、回归和耗时测量。
- 大表变更采用 expand → migrate → contract，避免一次阻塞性重写。
- 数据回填脚本可重复执行，记录批次、数量、哈希、失败行和完成时间。
- 每季度安装 PostgreSQL 当前小版本并先完成备份/恢复验证。
- 每年检查 PostgreSQL、MinIO、Node.js 和操作系统支持周期；主版本升级先做 `pg_upgrade --check` 与逻辑备份恢复演练。

## 9. 容量与性能

当前规模不需要分库、分片、读副本或审计表预分区。

容量管理采用可测量阈值：

- PostgreSQL 数据卷和 WAL 卷使用率达到 70% 预警、85% 阻断非必要批量导入。
- 对象存储达到 70% 预警、85% 停止非关键临时文件并扩容。
- 主版本升级前保证至少可容纳一份数据库副本和升级临时空间。
- 每月记录数据库大小、最大表/索引、审计增长、对象数量、对象总量和备份增长。
- 审计事件超过约 500 万行或单表超过约 50 GB 后，再基于实际查询模式评估按时间分区；不要提前引入分区复杂度。

附件容量按项目数量而不是员工数量估算：

`三年文件量 = 每年项目数 × 每项目平均照片/附件数 × 平均文件大小 × 版本与备份系数`

二期开始现场照片上传前，必须使用 3 个真实项目测量平均值并更新磁盘预算。

## 10. 监控与例行任务

至少监控：

- PostgreSQL/MinIO 健康、磁盘使用率和连接数；
- 最近成功基础备份、最近成功 WAL 归档、可恢复时间窗口；
- 最近对象异机复制时间和复制失败数；
- 迁移版本、失败迁移和长事务；
- 数据库引用缺失对象、无引用对象和哈希不一致；
- 审计写入失败；关键业务成功但审计失败必须产生高优先级告警。

例行任务：

- 每日检查备份、WAL 和对象复制状态；
- 每周执行备份一致性检查和孤儿文件报告；
- 每月容量报告和逻辑备份；
- 每季度恢复演练与 PostgreSQL 小版本维护；
- 每年依赖支持周期和三年容量预测复核。

## 11. 现有实现评审

### 已满足

- PostgreSQL 18、UUID、`numeric(...,4)`、`timestamptz`。
- 外键、唯一约束、正数/状态检查约束。
- 多表事务和报价 revision 乐观并发。
- 已发布基础库/规则与已提交报价的数据库触发器保护。
- 报价、成本和规则版本快照。
- 导入文件 SHA-256、导出内容 SHA-256。
- PostgreSQL 与 MinIO Docker 命名卷。

### 上生产前必须补齐

1. 当前 API 与数据库初始化共用 `POSTGRES_USER`；生产需拆分 cluster admin、migrator 和 app runtime。
2. 当前 MinIO 只配置 root 用户；需创建应用和备份专用访问密钥。
3. 当前报价导出以 `bytea` 保存在 PostgreSQL；需迁移到统一文件模块和 MinIO，数据库只保留引用与哈希。
4. 当前 `audit_events` 没有数据库级 append-only 保护；需增加权限和触发器门禁。
5. 当前只有命名卷，没有自动异机备份、PITR 配置、恢复脚本和恢复演练证据。
6. 尚无附件元数据、上传完成状态、私有下载授权和孤儿对象治理。
7. 尚无生产 `compose.prod.yaml`、备份状态监控和磁盘阈值告警。
8. 用户和凭据存在级联删除关系；生产运行账号应禁止删除用户，以停用账号保留历史归属。

## 12. 实施顺序

### P0：正式使用前

1. 确认云厂商、Windows Server 实例规格、嵌套虚拟化支持，以及采用自建还是托管 PostgreSQL/对象存储。
2. 建立生产数据库/MinIO分权账号。
3. 新增统一文件记录和 MinIO adapter，将报价导出迁出 `bytea`。
4. 加固审计 append-only 与项目/用户禁止硬删除规则。
5. 配置 pgBackRest、WAL/PITR、异机加密仓库和备份监控。
6. 配置 MinIO versioning、异机对象备份和孤儿检查。
7. 配置 7～14 天云主机/数据盘快照，明确其不作为数据库主备份。
8. 创建生产 Compose、备份/恢复 runbook，并在新实例完成首次全链路恢复演练。

### P1：二期施工前

1. 确认施工照片保留期与容量模型。
2. 实现大文件/批量照片上传、失败重试和未完成上传清理。
3. 为施工计划、节点、进展和工程变动建立追加/版本化模型。

### P2：三期财务前

1. 确认财务档案期限和敏感信息分类。
2. 建立追加式收付款、冲正和实际成本模型。
3. 完成财务幂等、日终对账、权限、备份和恢复专项验收。

## 13. 验收清单

- 容器重建后命名卷数据仍存在，但同时证明可从异机备份恢复到新卷。
- 能恢复到指定时间点，实测 PostgreSQL RPO ≤ 15 分钟、核心 RTO ≤ 4 小时。
- 能在没有原生产服务器的环境中恢复 PostgreSQL、MinIO 和应用。
- 能在原 Windows Server 云主机完全不可用时，用新云主机、异机数据库备份和对象副本恢复，不依赖原宿主机磁盘。
- app runtime 无法修改 schema、审计历史、已发布模板或已提交报价。
- 报价导出和附件不再以大型 `bytea` 存入 PostgreSQL。
- 删除或覆盖文件不会绕过版本控制和业务审计。
- 新版本部署能在生产副本上完成迁移并通过回归。
- 批准报价、施工变动和财务记录在基础库调价或后续更正后仍可还原历史口径。
- 连续三个月备份检查无未处理失败，且至少完成一次季度恢复演练。
